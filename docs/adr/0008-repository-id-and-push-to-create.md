# 儲存庫用不會變的編號找 Durable Object；push 到不存在的儲存庫就建立它

部分取代 [ADR 0005](0005-workers-oauth-provider-on-kv-first.md)：儲存庫的 Durable Object 不再用 `<owner>/<repository>` 這個名字找，`git` 請求也不再只查 KV。

第一段的儲存庫就是「某個名字的 Durable Object 裡剛好有資料」：程式用 `getByName("<owner>/<repository>")` 找到它，主機上沒有任何地方記著「有哪些儲存庫」。第二段要能在設定頁列出並刪除儲存庫，這樣就不夠了。我們改成：**每個使用者的使用者 DO 裡存一份儲存庫清單，記著名字與儲存庫編號 (Repository ID)**；儲存庫編號就是建立時用 `newUniqueId()` 產生的 Durable Object id，之後永遠不變。git 請求先問使用者 DO 拿到編號，再用編號找儲存庫的 Durable Object。R2 上 pack 的路徑本來就以 Durable Object id 開頭（ADR 0003），所以也跟著變成以儲存庫編號開頭。

改用編號，是因為刪除沒辦法一瞬間做完。R2 一次最多刪 1000 個檔案，大的儲存庫要在背景分好幾批刪。如果還用名字找，刪掉之後馬上用同一個名字重建，會對到同一個 Durable Object、同一個 R2 路徑：新的 push 寫進 `…/packs/1.pack`，背景那邊還在刪舊的，就可能把新資料一起刪掉。用編號的話，重建一定拿到新的 Durable Object 和新的 R2 路徑，兩邊結構上就撞不到。

## 建立與刪除

- **push 到不存在的儲存庫就建立它**，跟第一段一樣，不需要先呼叫什麼。建立算 `write` 權限範圍（ADR 0007）。之後 MCP 要建立儲存庫時，走同一個內部入口。
- **push 一開始就在清單裡登記**，寫任何資料之前。所以 push 失敗時，清單裡會多一個空的儲存庫，設定頁看得到、也刪得掉。這樣守住的規則是「R2 上每一份資料，都屬於清單裡的某一個儲存庫」，刪除一定清得乾淨。
- **刪除只能在設定頁做**（ADR 0007），而且要再打一次儲存庫名稱才能按下去。刪除時先把清單裡那一列拿掉，網址立刻就找不到它；舊的 Durable Object 接著在背景刪掉 R2 上的 pack，最後清空自己的 SQLite。刪了就救不回來。
- **名稱規則**：小寫英文、數字、`-`、`_`、`.`，1 到 100 字；不能是 `.` 或 `..`，不能以 `.git` 結尾。有大寫就拒絕，錯誤訊息裡提示小寫的寫法。刪掉的名稱可以再用：同一個擁有者底下的網址，不會被別人接走。

## 考慮過的選項

- **維持用名字找，刪除時標成「刪除中」**：背景清完之前不准用同一個名字重建。沒選，因為要多一個狀態，還要替「重建被擋」寫錯誤訊息；清單本來就得存，多存一個編號幾乎不多花力氣。
- **先建立才能 push**：打錯名字不會多出儲存庫，但每個儲存庫都要多一步設定，而 map 的方向是「一般 git 使用者幾乎不做設定就能用」。打錯名字的代價只是去設定頁刪一次。
- **push 成功才登記**：失敗時不會留下空的儲存庫，但失敗那次寫進 R2 的 pack，掛在一個清單裡沒有的編號底下，誰都看不到、也清不到。
- **刪除後保留幾天、可以救回來**：要多一個「已刪除但還在」的狀態和救回的畫面，目前用不到。
- **名稱允許大寫、比對時不分大小寫**（GitHub 的做法）：要同時存顯示用與比對用的兩種寫法，每個比對的地方都要記得轉。

## 後果

- 每個 git 請求多一趟使用者 DO 的呼叫（名字 → 編號）。ADR 0005 原本寫的是「每個 `git` 請求只查 KV、不經過使用者 Durable Object」，這一點不再成立。
- ADR 0005 說使用者名稱不能改的兩個理由之一是「儲存庫的 Durable Object 用名字找，沒辦法改名」，這個理由不再成立；另一個理由（權杖上帶著名稱）還在，所以名稱照樣不能改。
- 之後儲存庫要換名字或搬到組織底下，只要改清單那一列，資料不用動。
- 第一段留在正式環境上的儲存庫（Durable Object 用名字找、不在任何清單裡）不搬移，第二段上線時正式環境從空的開始；舊的 Durable Object 與 R2 上的 pack 用一次性的方式清掉，怎麼清由第二段的規格決定。目前上面只有兩個驗收用的測試 repo。
