# GC 不設寬限期：提交排進 push 佇列、比對變動次數；只重寫含有垃圾的 pack

接手 [ADR 0003](0003-pack-storage-split-sqlite-r2.md)〈後果〉裡「R2 裡的 pack 會留著沒人用，目前不清理」與「目前也不做 GC」這兩條。規格是 [#34](https://github.com/yurenju/fugitive/issues/34)。

背景：push 上來的 pack 原樣保存，SQLite 另有一張目錄表（`objects`），記每個物件在哪個 pack 的哪個位置（ADR 0003）。刪掉分支、force push 之後，從任何分支或 tag 都走不到的物件（垃圾）一直佔著空間。我們讓主機在背景自動清：可能產生垃圾的 push 之後 1 小時，儲存庫的 Durable Object 用 alarm 叫醒自己跑一次 GC。GC 分兩步：**準備**不排隊，跟 push 同時跑，算出走得到的物件，把「含有垃圾的 pack」裡還要留的物件複製進一個新 pack；**提交**排進 push 佇列，在一個 transaction 裡把目錄改成指向新 pack、刪掉垃圾的目錄列、把舊 pack 標成退役。退役的 pack 再留 1 小時才真的刪，讓提交前就開始的 clone 讀得完。

**跟 git、GitLab 不一樣，我們不設兩週的寬限期。** git 的 push 和 GC 是兩個互不知道的程序：GC 看得到一個剛寫進來、還沒掛上分支的物件，卻分不出它是垃圾還是 push 寫到一半，只好只刪「夠舊」的。我們的 push 本來就在儲存庫的 Durable Object 裡一個接一個排隊，GC 的提交也排在同一個佇列裡，所以提交的那一刻不會有 push 做到一半。剩下的問題是準備跟 push 同時跑：準備開始時記下 `meta` 裡的**變動次數**，提交時如果次數變了，就整輪放棄，等下一次觸發再來。有兩種事會讓它加一：分支或 tag 移動（包括新建、刪除），以及一個 pack 完整收下。

分支移動要算，是因為目錄的寫入是 `INSERT OR IGNORE`。使用者刪掉分支、準備步驟把那些物件判成垃圾，接著使用者把分支 push 回來：client 會把物件再送一次，但目錄裡原本那一列不會被蓋掉，它繼續指向準備要退役的舊 pack。照原計畫提交的話，這個分支就讀不出來了。

pack 收下也要算，是 code review 時發現的，規格 #34 原本只比對分支移動。準備期間有人 push 一個 thin pack，裡面的 delta 拿一個剛被判成垃圾的物件當底稿，但分支更新被拒絕（例如別人先推了）：分支沒動，pack 卻已經完整收下。照原計畫提交就會刪掉那個底稿；之後有人把分支指到這個 pack 裡的 commit，連通性檢查會過（commit 在目錄裡），delta 卻解不開。代價是準備期間只要有帶 pack 的 push，這一輪就放棄。

另外兩件事一起定下：

- **只重寫含有垃圾的 pack，不為了數量合併。** 每一個含有垃圾的 pack 都重寫（沒有「垃圾佔多少才重寫」的門檻），還要留的物件全部寫進同一個新 pack；全是垃圾的只退役不重寫。複製的是壓縮後的資料，只重寫每個物件的標頭：ofs-delta 的底稿已經在新 pack 裡就重算距離，否則改成 ref-delta。
- **delta 的底稿一律算走得到**（底稿的底稿也是）。要留的物件如果是拿一個走不到的舊版本當底稿存的，那個舊版本也留著，不必為了刪它而把 delta 解開重算。

## 考慮過的選項

- **照 git 的做法設寬限期、把走不到的物件先收進 cruft pack**：不需要跟 push 協調，但要多存每個物件的時間、多一種 pack，而且刪錯分支的內容反而會多留兩週，這台主機沒有人需要。
- **整個 GC 都排進 push 佇列**：最簡單，不需要變動次數；但大儲存庫的 GC 要讀完所有 pack，這段時間 push 全部要等。
- **定期把所有 pack 合成一個（git 的 `repack -a`）**：pack 的數量會一直增加，但現在量不出讀取有因此變慢，每次合併都要重寫整個儲存庫。等 MCP 段每個 commit 產生一個 pack、而且量得出變慢，再考慮 geometric repack。
- **重寫時把 delta 解開、重新壓縮**：新 pack 會比較小，但 CPU 是 Workers 上最先碰到的限制（ADR 0003）。
- **用 R2 的 lifecycle 規則清沒人用的 pack**：它只看檔案建立了多久，不知道檔案還有沒有人在用。

## 後果

- 走不到的物件大約在觸發後 1 小時消失，舊 pack 再過 1 小時才真的刪。刪錯分支的人在這之前 push 回來，內容就還在，但**這不是保證**，跟 git 在沒有 reflog 的伺服器上一樣。
- GC 跑完之前，知道 commit id 的人還是抓得到被蓋掉的 commit：fetch 不檢查要的物件是否從分支或 tag 走得到。現在儲存庫都是私有的，留給公開儲存庫那一段。
- 每個移動分支的入口都要經過 `updateRefs`（它透過 `setRef` 累加變動次數），並且在移動之後判斷要不要排 GC（`mayLeaveGarbage`）。之後 MCP 的伺服器端 commit 也一樣；它如果不經過 push 的 `finishIndexing` 就寫進新的 pack，也要自己把變動次數加一。
- 很常 push 的儲存庫，GC 可能一直被放棄。準備大多只花幾秒，應該很少碰到；log 裡的 `abandoned` 就是在記這件事。
- 一次 GC 假設在一個 alarm（最多 15 分鐘）裡做得完，不做成分段接著做；GC 丟例外時平台會重試 alarm，每次從頭做；最後一次重試還是失敗，就不再丟例外，改成清掉 GC 預定時間、照常排下一件事，所以退役 pack 的刪除不會跟著停。大儲存庫實際要多久，看 #34 手動驗收的數字。
- 一個 Durable Object 同時只能排一個 alarm，所以刪除儲存庫、刪退役的 pack、GC 三件事共用它：時間都記在 SQLite 裡，alarm 醒來依序做到期的事，再把 alarm 設成下一件事的時間。正在刪除的儲存庫只做刪除。
- pack 的編號不再重複使用（`meta` 另存一個遞增的計數）：R2 的 key 是用編號組的，退役的 pack 1 小時後才刪，編號重複的話，延後的刪除會刪到新的 pack。
- push 途中當掉留在 R2 的 pack，由下一個 push 開始時刪掉；那之前就留下、或刪失敗的，由 GC 準備步驟掃 R2 時刪掉（只刪 `packs` 表裡完全沒有對應列的 key）。
- 目錄沒有 CRC，複製壓縮資料前不像 git 那樣先檢查資料有沒有壞。這些資料 push 時已經解開、算過 SHA-1。
