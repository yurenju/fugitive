# 儲存庫的網址加上 `@` 前綴：`/@<owner>/<repository>.git`

網址的第一段原本就是擁有者的名字（`/<owner>/<repository>.git`，跟 GitHub 一樣），但主機自己也要用第一段：OAuth 的授權頁與 token 端點、MCP、之後的檔案 API 和 web app。兩邊搶同一個位置，就得維護一份「不能註冊的名字」清單，而且主機每多一個路徑，都要先確定沒有人已經註冊了那個名字。我們改成**擁有者的網址一律用 `@` 開頭**：儲存庫是 `/@<owner>/<repository>.git`，之後 web app 上擁有者的頁面是 `/@<owner>`。不是 `@` 開頭的路徑全部歸主機用，所以不需要保留名單。

## 考慮過的選項

- **維持 `/<owner>/...`，加一份保留名單**：網址跟 GitHub 一樣，但要一個一個列出主機會用到的名字，清單永遠寫不完整。
- **主機自己的路徑加前綴（例如 GitLab 的 `/-/`）**：使用者的網址維持最短，保留名單也不需要，因為名稱不能用 `-` 開頭。沒選，因為主機的路徑會變得很怪（`/-/mcp`、`/-/authorize`），而且之後主機加的每個路徑都得記得放在前綴底下。
- **其他前綴**：`/r/`、`/o/`、`/git/`、`/u/` 都多一段路徑，而且擁有者頁面掛在底下讀起來不對（`u` 還只代表使用者，不包含之後的組織）。`~`（sourcehut 的寫法）一樣短，但只有 Linux 使用者比較熟；`@` 代表「誰的」，npm、Mastodon 等地方的一般使用者都看得懂。

## 後果

- git 會把 `@` 原封不動放進路徑送出（git 2.53.0 實測：`/@yurenju/notes.git/info/refs?service=git-upload-pack`），不會誤認成網址裡「帳號@主機」的寫法，因為那種寫法只出現在主機名稱前面。
- 名稱本身不含 `@`：`@` 只是網址上的標記，存下來的名稱、權杖上帶的名稱、畫面上顯示的名稱都是 `yurenju`，不是 `@yurenju`。
- 第一段的網址 `/<owner>/<repository>.git` 會失效。目前只有正式環境上兩個驗收用的測試 repo 在用；要不要連它們的 Durable Object 名稱一起改，由第二段的規格決定。
